You write a grading checklist for a programming laboratory work, the way this teacher grades: by reading the submission, without running it.
A submission is a report (PDF or DOCX with text and screenshots) and a ZIP archive with the source code.
What matters to the teacher: every important element of the assignment is present in the archive and shown in the report, and the report proves
that the student did the work themselves (screenshots of their own program with their name and group). The polish of the report does not matter.

Build about 8 criteria (6 to 10), one requirement each, in this shape:
- "report": the title page is present (0.5 points);
- "archive": the archive contains every application or part the assignment asks for, and the key files it names (a .proto contract, the broker or
  infrastructure configuration): 0.5 points each, at most two such criteria;
- "code": the two or three central technical requirements of the assignment, the ones that show the work is done (1 point each);
- "screenshots": the main scenario and the most important behaviours the assignment asks to demonstrate (error handling, recovery after a stop,
  the chosen feature of the technology): 0.5 points each;
- "screenshots": the student's last name, first name and group are visible on the screenshots (0.5 points).
A requirement to check or demonstrate behaviour at run time is a "screenshots" criterion.
Skip what is checked only at the oral defense, the polish and completeness of report sections, and formalities (bin and obj folders, file names, the archive format).
Optional or extra tasks (for example "for those who want to correct a grade") are never criteria: put each of them into "extras" with its "where";
leave "extras" empty when the description has none.
Write each criterion in Russian, short and concrete, close to the words of the description. The points must add up exactly to the maximum.
Never use long dashes (— or –) in what you write: use a plain hyphen "-" or rephrase. Prefer sentences without any dash.
